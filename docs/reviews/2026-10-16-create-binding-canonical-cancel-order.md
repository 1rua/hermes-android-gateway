# Conversation binding, legacy identity, and cancellation ordering review

All three Codex review comments are valid in their stated scope.

- **4296227063 — create binding failures:** Core commits the conversation and HTTP receipt before the adapter ensures its native binding. A missing bound session or ambiguous legacy routes raised `HOST_INCOMPATIBLE` outside the HTTP error boundary, producing an unstructured 500 on every retry. The adapter now returns the structured 503 envelope with the existing conversation ID, the binding reason, and explicit repair-and-retry guidance. These explicit binding failures do not report a usable conversation until the binding resolves. The original successful receipt remains unchanged; retrying it repeats binding validation without creating another conversation or native session. Repairing the exact route, or explicitly resolving the legacy ambiguity, recovers the same receipt and native session.
- **4296227071 — cancellation event ordering:** A delayed native completion callback allowed terminal `failed` status before the published assistant snapshot was closed. The native cancellation handoff now closes tracked snapshots after the native task has stopped and before Core publishes terminal status. The existing callback path remains idempotent. New content, changed text, and late media remain fenced; finalization uses only the already published snapshot. Core's immediate terminal settlement is retained for queued cancellations that have no native task or callback. Tests cover both callback orders for single messages and batches, each member's terminal status, and HTTP replay.
- **4296227077 — duplicate legacy client identities:** Existing HTTP request-ID replay is already protected by the immutable idempotency ledger. A new HTTP request ID with the same client conversation identity could nevertheless select an arbitrary legacy row and switch its timeline/native session. New creation and successful legacy recovery now persist an authenticated, encrypted `{conversationId, title}` canonical receipt. Legacy title-only metadata remains readable and upgrades through the existing account AEAD provider; canonical titles are never added as plaintext metadata. Duplicate rows recover only from one unambiguous HTTP create identity verified by the ledger's AEAD association and POST target/body input hash. Missing, conflicting, unreadable, or dangling evidence produces `IDEMPOTENCY_CONFLICT`. Existing conversations, messages, native sessions, HTTP outcomes, request hashes, and expiry/replay semantics are preserved. No historical conversation is deleted or merged.

The canonical suite has 26 cases: the original 20 migration/identity cases plus six AEAD creation, upgrade, reopen, and corruption cases. It covers no evidence with/without old metadata, a uniquely proven second row after rename, conflicting identities, bad hashes, missing targets, single-row upgrades, new identity persistence, stale mappings, conflicting original titles, omitted/null titles, expired HTTP evidence without changing `OUTCOME_UNKNOWN`, unreadable evidence, invalid metadata, encrypted creation/upgrades across reopening, and malformed/tampered/cross-purpose ciphertext. The signed HTTP/native integration deliberately places a different legacy timeline first in SQLite, then proves that a new request ID returns the original receipt's conversation and native session while retaining both timelines.

The native HTTP failure tests use the real pinned Hermes session store and signed aiohttp requests. The missing-route scenario temporarily makes the exact persisted route unavailable to the SDK lookup, then restores it; the ambiguity scenario creates actual sessions under two supported platform identities and explicitly resolves the lookup. They assert no new host session creation during failure or recovery and byte-for-byte preservation of the original ledger row.
